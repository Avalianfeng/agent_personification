# agent 能力成本评估：自建到底贵不贵

> 写于 2026-08-16。承接 `04-结合定位.md` 的「手」与第四节分级，回答：
> 「agent 自带的能力如果自己实现，成本到底高不高？」
> 结论先行：**贵在通用外设与安全，不贵在灵魂；而这正是借与建的分界线。**

---

## 一、把「agent 能力」拆开看成本

「agent 能力」不是一件事，拆开之后成本差异巨大：

| 能力 | 自建成本 | 说明 |
|---|---|---|
| LLM 对话编排（agent-loop） | 中 | 轮子不少，但可自建 |
| 工具生态（文件/网络/shell/搜索/代码执行） | **高** | 每个工具都要实现、适配、维护、处理边界 |
| 会话与状态管理（append-only 日志、SQLite） | 中 | 我们本就要建的部分，且自建也不难 |
| 定时 / 后台任务 / 调度 | 中 | 成熟机制可抄 |
| 沙箱 / 审批 / 安全边界 | **高** | 隐性大成本，最容易被低估 |
| 透明轨迹（事件审计、可回放） | 中 | 我们自己能做，而且本来就要做 |
| 外部集成（Web UI / headless / SDK / JSON-RPC / ACP） | **高** | 面向通用场景的大量重复劳动 |
| 多模型路由 / 本地模型接入 | 中 | 我们可能只需要一个 `baseURL` |
| 稳定性 / 破坏性变更应对 | **高** | 框架预览期的自维护成本 |

---

## 二、成本结构结论

1. **贵在「外设与安全」，不贵在「内核」**。自建 agent 的大头是工具生态、外部集成、安全、稳定维护——全是通用重复劳动；
2. **我们的魂恰恰便宜**。State Core（几个连续变量 + 衰减 + JSON）、时间补算、Appraisal 规则——agent 没有，而且零依赖、低成本即可自建；
3. **中间层（会话 / 轨迹 / 调度）**：agent 现成，我们自建也不难——选择权在自己手里，但没必要重复造。

> 自建 agent 贵 ≠ 我们的项目贵。  
> 我们把贵的部分借来（工具、集成、安全、稳定），把便宜的部分自己建（状态、时间、评价、轨迹）——总成本曲线最低。

---

## 三、分场景：什么时候才值得自建 agent 能力

| 场景 | 判断 |
|---|---|
| 纯文本状态自演化机器 | 不需要任何 agent 能力；Phase 1 形态，零外部依赖 |
| 需要「主观意识驱动的动手」 | 需要**手**，但手可以借 agent 的，不必自建（自建一个能主动行动且安全可靠的实体，是极高的成本） |
| 需要完全脱离外部平台独立存在 | 才考虑自建全套 agent 能力——成本极高，现阶段明确不选，且与「以运行时为验证平台」的定位相悖 |

---

## 四、建 / 借分界线

| 层 | 建 or 借 | 依据 |
|---|---|---|
| 内核（魂） | **自建** | 便宜、差异化、真相层必须自己掌控 |
| 透明流程 | **自建** | 便宜，且是功能主义实验的检验手段 |
| 嘴（表达） | **借** | LLM 是通用能力，自建无意义 |
| 手（主动行动 / 外联 / 自迭代） | **借** | 自建成本极高，agent 现成且更强 |
| 验证机（对话产品层） | **借** | 自建 = 大量重复劳动 |

---

## 五、一句话

> agent 能力贵在通用外设与安全、便宜在灵魂；
> 我们自建便宜的魂与透明，借昂贵的嘴与手——成本最低，方向最正。
