## 二、状态图例

| 状态 | 含义 | 图例 |
|------|------|------|
| **已接受** | 决策已落定，作为后续设计与实现的前提 | `Accepted` |
| **已否决** | 曾作为候选路线被正式否决，记录否决理由 | `Rejected` |
| **已确认** | 由主人当面确认过的决策（区别于推演定稿） | `Confirmed` |
| **需思考** | 方向明确、形态未定，属于开放问题 | `Open` |
| **被取代** | 曾被接受、后被更强决策取代，转入归档 | `Superseded` |

## 三、写作原则（本体系遵守的 ADR 行为）

1. **决策有状态**：每条决策都标明 已接受 / 已否决 / 需思考，不写模棱两可的「也许应该」。
2. **背景先于结论**：每条决策先交代它要解决的分歧与语境，再给决策本身。
3. **后果随决策**：每条决策记录它带来的工程含义与约束，不另设「计划」章节。
4. **哲学与工程分层**：哲学总纲负责「为何」，模块地图负责「是什么、要满足什么」，决策记录负责「定了什么」。
5. **不写实现计划**：本体系不安排工期、不写任务清单；实现路线以决策形式存在（ADR-007 判定先后与边界）。具体到模块的**工程实现决策**（数学结构、数据结构、功能接口、调用链、验收标准）落在子目录 `实现路径/`——它仍是决策记录而非工期计划。
6. **原样保留张力**：未决之处如实标注「需思考」，不为了体系完整而假装已定。

## 五、读法建议

- **第一次读**：`000` → `001` → 四个决策文件（`002`~`004` + `006`）→ `005`，按此顺序形成「立场 → 模块 → 决策 → 未决」的完整认知。其中 `000` 文首「核心定位」应先读，它约束全文。
- **要动手实现**：先读 `实现路径/README.md` 与 `00-总览-构建线路与调用链.md`，再按需读对应模块文件；验收标准见 `10-路线-实施顺序与验收.md`。
- **查某条结论**：直接看对应决策文件的标题与状态行。
- **找未决事项**：`005-开放问题.md` 是本体系目前最活跃的部分，状态随每次决策迁移到 `001` 与决策文件。
