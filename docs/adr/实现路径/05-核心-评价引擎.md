# 05-核心-评价引擎（Appraisal）

> 状态：**已确定（原则）/ 待裁决（实现形态）**
> 定位：对应 `001-模块地图.md` 模块③——事件不直接改状态，先经评价。
> 承接：ADR-002（真相层写保护）、`001` 模块③ 条件、`005` 问题 2。

---

## 一、职责

- 情绪不是事件的直接映射，而是事件经价值观与上下文解释后的产物（Appraisal Theory：Lazarus、Scherer、OCC 等）；
- 同一事件「用户三天没回复」：
  - 评价为「他故意的」→ `trust` 降、`stress` 升；
  - 评价为「他只是在忙」→ 期待略降、联结略降；
- Agent 不直接 `sad += 20`，而是先完成评价，再更新底层状态变量。

## 二、原则（已定，不可违反）

1. **事件不直接改状态**：`applyEvent` 必须先评价，再经 `applyDelta` 更新（ADR-002）；
2. **评价先于情绪**：需求未满足 → 驱动状态变化 → 产生可感知倾向；不先写「sad=true」；
3. **评价链路可检查**：评价本身不能变成表演——它是在做评价，还是在生成「符合角色期待的评价」（`001` 模块③ 条件 4）；
4. **规则为主、LLM 辅助可关**（方向已定，形态未定）。

## 三、实现形态（待裁决，`005` 问题 2）

- **候选**：
  1. **纯规则表**（推荐 Phase 3 起点）：JSON 规则表 `{ 事件类型 + 条件 → 评价 → delta }`；
  2. 小模型：本地分类/评分模型（后置，需评估）；
  3. **LLM 辅助（可关）**：LLM 输出**结构化评价 JSON**，经**规则校验器**通过后才应用。
- **推荐**：先纯规则表跑通，再开 LLM 辅助开关；LLM 永远只给「评价建议」，不直接写状态。
- **决策规则**：Phase 3 裁决；规则表的形态在 Phase 1 `apply-event` 的简化规则中先长出雏形。

## 四、评价数据结构

```json
{
  "event_id": "evt-00123",
  "ts": "2026-08-16T12:00:00.000Z",
  "appraisal": {
    "valence": -0.4,
    "attribution": "external | internal | chance",
    "relevance": 0.8,
    "urgency": 0.2
  },
  "deltas": [
    { "var": "connection", "delta": -0.05, "reason": "对方三天未回复，解释为在忙" }
  ],
  "source": "rule | llm-aux"
}
```

- `deltas` 是**唯一**被 `applyDelta` 接受的增量载体；
- `source` 区分规则与 LLM 辅助，供审计（防表演检查项）。

## 五、规则校验器（已定方向，参数 Phase 3 定）

- 变量白名单（只能改已定义变量）；
- delta 范围钳制（如 `|Δ| ≤ 0.2`/事件，惯性约束）；
- 单事件 delta 总量上限（防一次事件掀翻状态）；
- 来源标记必填；LLM 输出缺字段或越界 → 拒绝并落迹（拒绝也算轨迹）。

## 六、防表演（ADR-002 后果、`001` 模块③ 条件 4）

- 评价链路全量落迹：`event → appraisal → deltas → applied` 每一步可查；
- LLM 辅助评价的输入是「事件 + 当前状态摘要」，输出结构化 JSON；
- 检查点：「这个评价是在解释事件，还是在迎合『它该有的反应』？」——通过轨迹回放即可检验（ADR-006）。

## 七、调用顺序（完整链路）

```
事件进入
  → ① 时间补算（先让时间流逝，见 04）
  → ② 评价（规则表 或 LLM 辅助 → 校验器）
  → ③ applyDelta 应用（白名单校验 → 落迹 → 原子写回）
  → ④ 状态快照（供摘要/下一轮）
```

## 八、验收（Phase 3）

1. 同一事件、不同评价 → 不同状态轨迹（ADR-007 原文验收）；
2. 「三天没回复」的两种评价路径可在轨迹中完整回放；
3. LLM 辅助可关；关闭后规则表仍能闭环；
4. 任何评价可检查（谁、为什么、改了什么、是否越界）。
