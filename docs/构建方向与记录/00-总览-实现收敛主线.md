# 00 总览 — 实现收敛主线

> 来源：2026-08-17 协作 AI 建议（「实现设计收敛过程」），本目录按此组织。
> 地位：本文件是**讨论过程的框架**，不是决策本身；具体决策在 `docs/adr/` 与 `docs/adr/实现路径/`。

## 一、核心原则

1. **数学先于代码**：先搞清「这个东西在数学上到底是什么」，再决定代码怎么写。
2. **代码只是数学模型的执行器**：数学决定 `x(t)=b+(x0−b)·e^(−kΔt)`，代码只是 `decay(...)`；禁止反过来「因为代码方便，所以状态这样演化」。
3. **反模式（禁止）**：先写 JSON → 再写变量 → 再写 if → 发现行为不对 → 加参数 → 加规则 → 加特例 → 最后变成一堆经验规则。
4. **数学复杂度不先于系统需求**：能用 L1 就绝不上 L3。
5. **复杂度预算**：复杂度不会凭空消失，只会转移到模型、参数、数据、计算、表示或解释层。不问「哪个地方最简单」，而问「整个系统的复杂度被放在哪里」（`C_total = C_state + C_dynamics + C_appraisal + C_memory + C_computation + C_parameterization`，思想性公式，不真算）。
6. **设计路线**：观察现象 → 寻找已有理论 → 提取功能 → 判断必要性 → 设计机制 → 选择数学表示 → 工程实现。数学结构的选择是理论驱动的（解释能力 / 计算成本 / 可观测性 / 可验证性），不是「简单先用，不好再换」。
7. **外部研究优先**：凡涉及「人类为什么会这样 / 机制是否真实存在 / 是否遗漏某种心理机制」，先查文献（心灵哲学 / 认知科学 / 心理学 / 神经科学 / AI·ML），不凭自我观察直接设计——防止「把恰好容易被意识观察到的部分，当成心智全部的因果结构」。

## 四、数学模型成熟度 L0~L6

| 等级 | 模型 | 启用条件 |
|------|------|---------|
| L0 | 经验模型（查表/规则堆） | 起点避讳：一上来就 L0 会滑向反模式 |
| **L1** | **确定性动力系统**（如 dx/dt=−k(x−b)） | **Phase 1 只要求这一级** |
| L2 | 耦合动力系统 | 状态本体收敛后若出现强耦合需求 |
| L3 | 随机过程 | 出现不确定性/噪声无法忽略时 |
| L4 | 状态空间模型 / Bayesian | 需要滤波/置信度时 |
| L5 | 非线性动力系统 / 吸引子 / 稳定性 | 需要长期行为分析时 |
| L6 | 学习型动力学 | 出现数据驱动需求时 |

规则：升级必须由**具体需求**触发，禁止先升级再找需求。

## 五、横向轴（每个阶段都必须回答）

```text
定义 → 假设 → 数学/逻辑 → 实现 → 可观测量 → 验证 → 失败怎么办
```

- 可观测量：这个阶段产生什么可观测的东西？（状态值、轨迹、CLI 输出…）
- 验证：怎么证明它按设计运行？
- 失败怎么办：预测失败时，问题出在哪个环节、如何定位。

## 六、关键验收句（贯穿全程）

1. **拿掉 LLM，内在系统仍然存在**（架构验收，接 LLM 前必须成立）。
2. 项目的终点不是「代码写出来了」，而是「**观察到由历史和时间产生的、可重复验证的内部状态系统**」。
