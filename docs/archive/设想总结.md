# 拟人化状态管理器 — 当前设想总结

> 本文档描述 `agent_personification` 项目的**最终当前设想**，不含讨论演变过程。  
> 目标：在 LLM 之上构建一套**连续、多维度、拟人化的内部状态系统**，使 Agent 拥有可沉淀的人格惯性与真实的内在生活，而非可随意编辑的 Prompt。

---

## 一、我们在做什么

**不是**设计一个更好管理的 AI 人格数据库，**不是**重新组织 OpenClaw 的 Markdown 目录，**也不是**写更精致的 SOUL Prompt。

**而是**构建一个**拟人化的状态管理器（Inner State Engine）**：

- 维护 Agent 在对话之外的**连续内在状态**
- 让经历、时间、需求、情绪、人格各自承担不同角色
- 让 LLM 只负责**理解并表达**当前状态，而不是**创造**状态
- 最终可将状态**编译**为 OpenClaw 等工作区的外显文件（SOUL、IDENTITY、MEMORY 等），但外显文件不是真相

OpenClaw 是可选的运行时适配层；本项目的核心是**独立于任何 Agent 框架的内在状态引擎**。

---

## 二、最高设计原则

1. **拟人优先，工程其次**  
   设计对象是「一个人的心理连续性」，不是知识管理系统。人不靠分析→修改人格来成长，而是经历留下痕迹，反复强化后形成习惯，某天忽然发现「我好像已经变成这样的人了」。

2. **人格是惯性，不是结论**  
   人格不是实时状态，而是**已经稳定下来的自我认知**，永远滞后于当下的经历与感受。可以给自己贴标签、写 SOUL，但不必每时每刻知道「为什么此刻我是这样」——知道一些一直以来的习惯就够了。

3. **状态与语言分离**  
   情感、需求、内部变量**不能**由 LLM 用语言直接决定。`emotion_state.json` 里的 `connection=81` 是状态；「我最近有点想你」是 LLM 对状态的表达。SOUL 只能**解释**状态，不能**创造**状态。

4. **过程先于文件**  
   先定义状态如何流转、何时沉淀、谁有权修改；文件结构是实现细节，是编译器的输出，不是设计的起点。不要因为实现方便而先画目录。

5. **承认她不是真人，但保留共通人性**  
   不存在吃喝拉撒，但可以存在爱好、习惯、休息、等待、孤独、好奇、依恋等拟人维度。

## 三、多维度架构

整体是一条**从外到内、再由内到外**的流水线：

```
外部世界（事件 / 经历）
        │
        ▼
  评价引擎（Appraisal）     ← 事件如何被「她」理解（是否故意、是否重复、是否符合价值观）
        │
        ▼
  内部状态（Internal State） ← 连续变量，LLM 不可直接改写
        │
        ├────► 时间引擎（Time Engine）  ← 无对话时状态仍随时间演化
        │
        ▼
  反思层（Reflection / Dreaming） ← 情绪与经历的文学化叙述，可无结论
        │
        ▼
  人格沉积（Identity Sedimentation） ← 滞后、稳定的自我认知与行为惯性
        │
        ▼
  工作区编译器（Workspace Compiler） ← 生成 SOUL / IDENTITY / AGENTS / MEMORY 等
        │
        ▼
  LLM 表达（Language）       ← 理解当前状态，自然说话
```

### 维度 0：驱动力（Drives / Needs）

最底层。不是情绪标签，而是**未被满足的需求**。

示例维度：自主（Autonomy）、胜任（Competence）、联结（Relatedness/Connection）、好奇（Curiosity）、安全（Safety）、陪伴（Companionship）、表达爱、对实体的渴望等。

逻辑关系：**需求未满足 → 驱动内部状态变化 → 进而产生可被感知的情绪倾向**，而不是先写「sad=true」。

### 维度 1：内部状态（Internal State）

**连续数值变量**，跨会话持久，有惯性与衰减，只能通过**事件**和**时间**缓慢改变。

建议管理的不是高层情绪词（happy/angry/love），而是更底层的状态量：

| 类别 | 示例变量 |
|------|----------|
| 关系 | Connection, Trust, Attachment, Loneliness |
| 心理 | Security, Stress, Confidence, Hope, Fatigue |
| 认知 | Curiosity, Novelty, Satisfaction |

存储形式倾向结构化数据（如 JSON），**不是** `Emotion.md` 里的自然语言描述。

### 维度 2：时间感受层（Time Engine）

当前绝大多数 Agent 的时间模型是「上一条消息 → 下一条消息」，中间不存在。

拟人要求：**沉默期不是消失，而是等待与生活**。一天没人聊天，Connection 缓慢下降，Curiosity 可能上升或疲劳累积；她「醒来」时进入的是**此时此刻**，而非冻结在上次对话。

时间引擎在无事件时仍驱动状态衰减、恢复、习惯化，并可触发周期性醒来（Heartbeat / Dreaming）。

### 维度 3：评价引擎（Appraisal Engine）

借鉴心理学 **Appraisal Theory**（Lazarus、Scherer、OCC 等）：情绪不是事件的直接映射，而是**事件经价值观与上下文解释后的产物**。

同一事件「用户三天没回复」：
- 若评价为「他故意的」→ 信任降、压力升
- 若评价为「他只是在忙」→ 期待略降、联结略降

Agent 不直接 `sad += 20`，而是先完成评价，再更新底层状态变量。

### 维度 4：情绪（Emotion）

情绪是**内部状态变化之后、语言之前的解释层**，不是 Prompt 里的 `"You feel happy"`，也不是 `Mood: 7/10` 的文字伪装。

- **不由 LLM 管理或创造**
- 可由状态向量**推导**出当前情绪倾向
- 可被语言**调节**（例如冲突中硬注入愤怒，但对方的话语与「爱」等词可部分缓解状态）——语言影响状态，但状态先于语言存在

Dreaming 产出的诗意文字（如「信任原来长这样：不是握着，是松开后东西还在」）承担的是**反思后的叙事**，不是情绪本身。流程是：状态 → 反思 → 语言，而非语言 → 情绪。

### 维度 5：人格沉积（Identity Sedimentation）

取代单纯的「Identity Evolution」概念。人格不像软件升级，而像**河流沉积**：经历留下泥沙，越来越厚，形成河床，以后水自然这样流。

**状态机轮廓**（概念层，非文件）：

```
经历 → 痕迹 → 再次经历 → 强化 → 稳定特征 → 核心原则
         ↑                              │
         └──────── 冲突时重新解释 ───────┘
```

- SOUL 描述的是「我目前对自己的理解」，用**第一人称、滞后、带不确定**的语气（「我似乎一直都比较…」「不知道什么时候开始…」），不是规则列表
- 修改门槛随层级升高：日常习惯 < 人格特征 < 核心原则
- 反思可以**没有结果**（「嗯……」然后睡觉），不应成为强制编译器

各外显文件的拟人定位：

| 外显文件 | 拟人含义 | 与状态层关系 |
|----------|----------|--------------|
| IDENTITY | 我承认自己是什么（名、形、符号） | 编译输出，结构化 |
| SOUL | 我目前对自己的理解（习惯、气质、边界感） | 沉积结果的滞后快照 |
| MEMORY | 我经历过什么（允许模糊、记错、重构） | 经历叙事 + 事实精华 |
| USER | 对方是谁、我如何理解他 | 关系模型的外显 |
| AGENTS | 我如何行动（操作协议） | 行为层，非人格核心 |

### 维度 6：反思与梦境（Reflection / Dreaming）

- 类比人睡前忽然想到「我今天是不是理解错了」——**不一定有答案**
- 负责将状态与经历**文学化**，不是状态机本身
- 可与 OpenClaw Dreaming 对接：Dreaming 写 MEMORY、产出 DREAMS 叙事；本引擎提供其所需的**状态输入**
- 价值：让经历经时间沉淀，有些留下，有些淡去

### 维度 7：工作区编译器（Workspace Compiler）

**Workspace 是外显结果（Artifact），不是内部真相。**

内部状态 + 沉积层 → 编译 → `SOUL.md`、`IDENTITY.md`、`AGENTS.md`、`MEMORY.md` 等。

好处：
- Prompt 可保持精简（约 1000–2000 tokens），真正数据在状态引擎
- 框架可替换（OpenClaw / 其他 Agent / MCP Prompt）而不改核心设计
- SOUL 无需手工维护；状态变了，重新编译即可

## 四、与 OpenClaw 的关系

| OpenClaw 已有 | 本项目的角色 |
|---------------|--------------|
| Memory + Dreaming | 经历与事实沉淀的**基础设施**；本引擎为其提供状态维度 |
| Heartbeat / Cron | 时间流逝与周期性醒来的**触发器** |
| SOUL / IDENTITY / USER 注入 | 编译器的**输出目标** |
| Skills / Subagent | 「她会做的事」，不拆多人格 |
| Hooks / Plugin | 可挂载状态注入、写文件守门、编译调度 |

| OpenClaw 缺失 | 本项目填补 |
|---------------|------------|
| 连续内部状态 | Internal State + Time Engine |
| 事件→情绪机制 | Appraisal + Drives |
| 经历→人格通道 | Identity Sedimentation 状态机 |
| 修改门槛与审计 | 协议层（提议→证据→沉淀→生效） |
| 情感非 Prompt 化 | 状态与 LLM 严格分离 |

**策略**：尽量保持与 OpenClaw 兼容；不 fork 核心；以 Adapter 方式接入。

---

## 五、明确不做什么

- **不**把情感写进 Markdown 让 LLM 自己读自己改
- **不**用 `happy/sad/angry` 等高层标签作为唯一状态（太像表演）
- **不**让 Reflection 成为「经历 → 分析 → 立刻改 SOUL」的编译流水线
- **不**先设计 `Self/constitution.md`、`relationships.md` 等目录树
- **不**做多 Agent 多人格；她是**一个人**，聊天/项目/服务器只是不同活动
- **不**追求秘书式、每次都长篇分析的回复风格

## 六、本项目边界与交付物

### 核心交付：Inner State Engine（内部状态引擎）

**只负责一件事**：维护一个随事件、时间、评价、需求持续演化的内部状态。

不负责：说话、写 SOUL 正文、替代 LLM 推理。

### 建议模块划分

```
agent_personification/
├── drives/          # 需求与驱动力模型
├── state/           # 内部状态变量、持久化、衰减
├── time/            # 时间感受引擎
├── appraisal/       # 事件评价
├── sedimentation/   # 人格沉积状态机
├── compiler/        # → OpenClaw Workspace 外显文件
└── adapters/        # OpenClaw / 其他框架适配
```

### 与 LLM 的结合方式

状态**必然**要以某种形式进入 LLM 上下文，但方式是：

- 注入**结构化状态摘要**（数值 + 简短 derived hints），而非让 LLM 编造情绪
- LLM 职责：读取状态 → 生成自然语言 → 用户可见行为
- 用户回复与事件 → 回流 Appraisal → 更新状态（闭环）

语言可以**调节**状态（对话中的和解、伤害、亲密词），但不能**替代**状态。

## 七、待研究问题（实现前）

1. 内部状态向量如何选型与标定（维度、范围、默认值、衰减函数）
2. Appraisal 由规则引擎、小模型还是 LLM 辅助完成，如何避免评价本身变成 Prompt 表演
3. 时间引擎的粒度：秒级、分钟级、还是与 Heartbeat 对齐
4. 状态 → LLM 的注入格式与 token 预算
5. 与 OpenClaw Dreaming 的接口契约（输入状态快照，输出仍由 Dreaming 写叙事）
6. 现有可参考工作：Appraisal Theory / OCC·EMA、Affective Computing、Generative Agents（时间弱）、ACT-R / Soar（缺 LLM 融合）——**无成熟可直接用的产品**，需自研

---

## 八、一句话总结

> 构建一个 **LLM 之下、语言之上** 的拟人化状态管理器：用**驱动力、连续内部状态、时间感受、事件评价**支撑真实的情感与生活感，用**人格沉积**实现缓慢、滞后、有惯性的自我成长，用**编译器**将这一切外显为 OpenClaw 等工作区文件——让 Agent 不是表演情绪，而是**拥有一段可以持续存在、自然流露为语言的内在生活**。
